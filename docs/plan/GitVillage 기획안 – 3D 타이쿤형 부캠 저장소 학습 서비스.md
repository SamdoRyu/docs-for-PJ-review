## 프로젝트 개요

오피스는 부트캠프 팀 프로젝트를 위한 LMS로, 팀 레포 하나를 3D 사무실 하나로 보여줍니다. PR을 두고 팀원끼리 의견을 내고 토론하는 과정 자체가 부캠의 학습이라고 보고, PR, 이슈, 도움 요청, 배운 점 공유, 기타 무엇이든 회의실 안건으로 올려 함께 토론하게 만드는 것이 핵심입니다. 관리(일의 흐름)와 배움(리뷰·회고의 흐름)을 같은 GitHub 데이터 위에서 다루고, 세부 요구사항은 요구사항 정의서 v0.1의 ID를 따릅니다.

## 문제 정의 및 목표

부캠 팀 프로젝트는 2주 안에 끝나서 막힘이 하루만 방치돼도 일정이 무너지고, 끝난 뒤에는 배운 것이 이슈와 PR에 흩어진 채 면접 직전까지 정리되지 않습니다.

**기존 방식의 한계**

- PR이나 이슈에 대한 의견이 GitHub 코멘트 안에 묻혀 있어서, 팀이 함께 짚고 넘어가며 배울 자리가 없습니다.
- 누가 리뷰를 기다리는지, 어떤 이슈가 멈췄는지는 GitHub 목록을 하나씩 열어봐야 알 수 있습니다.
- 명세 문서의 요구사항과 실제 이슈·PR이 연결되지 않아, 빠진 요구사항이 마감 직전에 발견됩니다.
- 기획, 자료조사, 발표 준비처럼 코드로 남지 않는 기여는 GitHub에 기록되지 않습니다.
- 회고 문화가 없어서(ASM-06) 내가 내린 기술 결정과 그 이유를 면접에서 깊이 설명하기 어렵습니다.

**프로젝트 목표**

1. PR, 이슈, 도움 요청, 배운 점 공유, 기타 무엇이든 회의실 안건으로 올려 함께 토론하는 과정을 3D 사무실에서 보이게 해서 배움의 흐름을 만든다.
2. 팀 레포 하나를 사무실로 보여주고, 요구사항을 구역으로 나눠 명세 → 이슈 → PR 사슬을 한눈에 보이게 한다.
3. 활동량이 아니라 막힘, 대기, 편중을 보여줘서 도움이 필요한 사람을 먼저 드러낸다.
4. 코드 밖의 기여까지 포함해 개인 회고 리포트로 정리한다. 면접 꼬리질문 연습은 후순위 기능으로 둔다.

## 사용자와 역할

역할은 팀 레포의 GitHub 권한과 레포 관리자의 강사 지정으로 정해집니다. GitHub 조직이 가장 큰 단위이고 조마다 별도 조직이며, 앱은 조마다 조직에 설치합니다. 학생(참여자 · 레포 관리자)은 자기 조 조직에 등록된 레포만 보고, 등록된 레포가 여럿이면 드롭다운으로 골라 봅니다. 강사는 콜라보레이터로 추가된 모든 조의 레포를 같은 드롭다운으로 오가며 봅니다. 조 간 비교 화면 · 수치는 강사에게도 없습니다 (2026-10-30 결정 — 정의서 ASM-02와 다름).

| ID | 역할 | 정해지는 방법 | 이 기획에서의 필요 |
| --- | --- | --- | --- |
| ROLE-01 | 참여자 (팀원) | 팀 레포 콜라보레이터 중 레포 관리자 · 강사가 아닌 사람 전원(read 포함) | 막혔을 때 빨리 드러나고, 내 작업을 회고 리포트와 면접 준비로 남기고 싶음 |
| ROLE-02 | 레포 관리자 (팀장) | 팀 레포 admin 권한 | 요구사항 진행률과 막힘을 한눈에 보고 회의를 진행하고 싶음. 레포 주인으로서 레포 등록(사무실 열기)과 팀 설정(강사 지정 포함)을 맡음 |
| ROLE-03 | 전체 관리자 (1명) | 서버 설정에서 지정 | 사무실 관리 권한과 사용자·권한 관리 |
| ROLE-04 | 강사 | 팀 레포 콜라보레이터 중 레포 관리자가 앱 팀 설정에서 강사로 지정한 사람 | 모든 조의 사무실을 보고(개인 지표 포함), 학생이 요청한 건(도움 요청 답변 · 꼬리질문 · 결정 피드백)에만 답하고 싶음. 컨벤션 라이브러리를 올려 둠 |

**강사 (2026-10-30 결정)**: 팀이 강사를 GitHub 레포 콜라보레이터로 추가하고, 레포 관리자가 앱 팀 설정에서 참여자 목록 중 그 사람을 강사로 지정합니다. 지정 · 해제는 바로 반영됩니다 (FR-AUTH-06). 강사는 기본 보기 전용이고, 쓰기는 학생이 요청한 건과 컨벤션 라이브러리에서만 열립니다. 그 밖의 쓰기는 API가 거부합니다 (FR-AUTH-08). 강사는 팀원이 아니어서 책상 · 아바타가 없고, 스탠드업 참석자 · 평가 인원 · 담당 뷰 · 팀 지표에 들지 않습니다.

**대표 시나리오**

1. 팀장이 GitHub로 로그인해 우리 조 레포를 고르고, 명세 문서 경로와 프로젝트 기간을 넣습니다. 여기까지 5분 안에 끝납니다 (NFR-01).
2. 첫 동기화가 끝나면 사무실에 팀원 수만큼 책상이 생기고, 명세 문서의 ## 제목마다 바닥 구역이 생깁니다.
3. 이슈 상자가 상태에 따라 백로그 선반, 담당자 책상, 검토, 완료 선반으로 옮겨지고, 팀장은 연결 안 된 상자를 구역으로 끌어다 놓습니다.
4. PR이 올라오면 팀원들이 삼각기둥을 눌러 추천·비추천과 그 이유를 남깁니다. 평가는 PR을 보는 척도일 뿐이고, 머지는 GitHub에서 사람이 판단합니다. 함께 토론할 거리가 보이면 PR이든 이슈든 누구나 회의실로 끌어다 놓아 안건으로 올립니다.
5. 매일 아침 팀원이 스탠드업을 남기면 "어제 한 일"이 GitHub 활동으로 미리 채워지고, 회의실에서 막힌 이슈와 팀원들이 올린 안건을 다룹니다.
6. 막힌 팀원이 도움 요청에 "강사에게 요청"을 켜면, 강사가 게시판의 그 글이나 강사 요청함에서 답합니다. 강사가 답해도 도움 요청 상태는 바뀌지 않고, 해결은 요청자가 닫을 때 정해집니다.
7. 프로젝트가 끝나면 각자 회고 리포트를 만들고, 리포트의 기술 결정 카드와 학습 타임라인을 다듬어 마크다운으로 블로그에 올립니다.

## 3D 사무실 시각화

레포 하나가 사무실 하나이고, 그 안의 공간은 요구사항 구역과 작업 상태로 나뉩니다. 표현은 기존 3D 팀 오피스를 참고하고, Cities: Skylines에서는 구역 지정과 정보 뷰 두 가지 개념만 빌려옵니다.

**사무실 공간 구성**

사무실은 개인 책상, 공용 게시 공간, 회의실 세 공간으로 나뉩니다. 도형은 종류, 위치는 단계를 나타냅니다.

| 공간 | 성격 | 놓이는 것 |
| --- | --- | --- |
| 개인 책상 | 내 작업 | 내가 맡은 이슈, 내 PR (리뷰 중인 PR은 기존대로 검토 영역) |
| 공용 게시 공간 | 모두가 보는 것 | 도움 요청, 배운 점 공유, 회의 결정 기록 (공지는 두지 않는다) |
| 회의실 | 함께 논의하고 정할 것 | 확정된 안건 |

- 도움 요청과 배운 점 공유는 게시판이 기본 자리이고, 논의가 필요할 때만 회의실로 올립니다.

- 검토 영역, 백로그·완료 선반, 요구사항 구역은 지금처럼 둡니다.

## 배움의 흐름: 회의실 안건과 토론 학습

토론으로 배울 거리가 있으면 PR, 이슈, 도움 요청, 배운 점 공유, 기타 무엇이든 레포 참여자 누구나 회의실 안건으로 올리고, 회의에서 팀이 함께 토론해 결정과 배운 점을 남깁니다. 이 과정이 사무실에서 보이게 하는 것이 이 기획의 중심이고, PR 추천·비추천 평가는 PR을 바라보는 평가 척도일 뿐이고 머지의 계기가 아닙니다. 앱에서는 머지할 수 없고, 머지는 GitHub PR 페이지에서 사람이 판단해 직접 합니다. GitHub의 리뷰 기능을 옮겨오는 것이 아니라 앱 자체 기능이고, 평가와 회의 기록은 앱 서버에만 저장합니다 (CON-02).

**회의실 안건 올리기**

안건을 올리는 데는 평가, 승인, 개수 제한이 없습니다. 함께 토론해 배울 수 있겠다고 느끼면 레포 참여자 누구나 바로 올립니다.

안건은 아래 5종입니다. 일에 관한 안건은 GitHub에서, 배움에 관한 안건은 앱에서 옵니다. 서비스의 핵심 원칙인 "일은 GitHub, 정리는 앱"과 같은 구도입니다.

| 안건 종류 | 출처 | 포함하는 것 | 올리는 방법 |
| --- | --- | --- | --- |
| 이슈 | GitHub | 멈춘 작업, 담당자 없는 작업, 브랜치에서 작업 중인데 PR이 오래 안 올라온 작업 | 이슈 상자를 회의실로 드래그 |
| PR | GitHub | 리뷰 대기, 해결 안 된 리뷰 스레드, 병합 충돌 | PR 삼각기둥을 회의실로 드래그 (평가 결과와 상관없이) |
| 도움 요청 | 앱 | 학습 일지의 "막힌 것", 답 없는 도움 요청 | 게시판에서 풀리지 않으면 요청자가 전환하거나 자동 후보를 확정 |
| 배운 점 공유 | 앱 | 팀 전체가 알면 좋을 배운 점 | 게시판 글을 회의실로 올리거나 회의실에서 안건 카드 작성 |
| 기타 | 앱 | 설계·규칙 결정, 코드 밖 작업, 외부 변화, main 직접 푸시 | 회의실에서 안건 카드 작성 (예: 배포 방식, 일정 조정, 역할 분담) |

브랜치와 커밋은 별도 안건 종류로 두지 않습니다. PR 없이 오래 작업 중인 브랜치는 연결된 이슈의 상태로, main 직접 푸시는 기타 안건으로 다룹니다.

**확정 방식**: 앱이 자동으로 찾은 안건 후보(답 없는 도움 요청, 리뷰 대기 PR 등)는 반투명으로 표시됩니다. 안건 올리기 버튼을 누르거나 회의실로 드래그하면 불투명하게 바뀌며 안건으로 확정됩니다. 사람이 직접 만드는 안건(배운 점 공유, 기타)은 바로 확정 상태로 생성됩니다.

**게시판에서 회의실로**: 도움 요청과 배운 점 공유는 공용 게시 공간에 먼저 붙고, 논의가 필요할 때만 회의실 안건으로 올립니다. 회의에서 정해진 결정은 게시판에 결정 기록으로 붙습니다. 팀원 누구나 결정 기록에 강사 피드백을 요청할 수 있고, 피드백은 결정 기록 아래 팀 전체에게 보입니다 (FR-LRN-22). 도움 요청이 안건이 되는 과정은 아래 도움 요청 흐름을 따릅니다.

안건 카드는 제목만 있으면 올라가고, 배경이나 지금까지 해 본 것은 쓰고 싶을 때만 씁니다. 회의에서 할 일이 생기면 "이슈로 만들기"로 내용이 채워진 GitHub 새 이슈 화면으로 넘어가고, 이슈 작성은 GitHub에서 합니다 (CON-02).

**도움 요청: 게시판에서 먼저, 안 풀리면 회의 안건으로**

도움 요청은 공용 게시 공간에서 팀원 코멘트로 먼저 풀고, 48시간 안에 풀리지 않으면 회의 안건으로 올립니다.

| 단계 | 위치 | 일어나는 일 |
| --- | --- | --- |
| 열림 | 게시판 | 학습 일지의 "막힌 것"이나 직접 작성으로 도움 요청이 붙음 |
| 논의 중 | 게시판 | 팀원들이 코멘트로 답함. 요청자가 "강사에게 요청"을 켰으면 강사도 답함 |
| 해결 | 게시판 → 닫힘 | 요청자가 닫음 |
| 안건 후보 | 게시판 (반투명) | 48시간 안에 해결되지 않음 |
| 안건 | 회의실 | 버튼이나 드래그로 확정되어 회의실로 이동 |
| 종료 | 닫힘 | 회의에서 해결되거나, 이슈로 만들기로 결정 |

1. 요청자가 닫으면서 도움이 된 코멘트를 고르고(코멘트 작성자의 "내가 도운 기록"에 남음), 배운 점 한 줄을 남깁니다.
2. 안건 전환은 요청자의 수동 전환과, 48시간 미해결 시 자동 후보 두 가지입니다. 자동 후보도 사람이 확정해야 안건이 됩니다.
3. 코멘트 기록은 안건에 그대로 붙어 회의실로 갑니다. 같은 도움 요청 구가 옮겨 가는 것입니다.
4. 회의에서 큰 작업으로 판명되면 이슈로 만들기로 결정하고 닫습니다. 이슈는 팀원이 GitHub에서 직접 만들고, 결정은 게시판에 남습니다.
5. 강사는 모든 도움 요청을 보지만, 답은 요청자가 "강사에게 요청"을 켠 글에만 답니다. 강사 답변은 "도움이 된 코멘트"로 고를 수 없고, 강사가 답해도 상태는 바뀌지 않습니다(해결은 요청자가 닫을 때만, 48시간 안건 후보도 그대로). 안건으로 전환하면 강사 답변도 코멘트 기록과 함께 붙습니다 (FR-LRN-21).

PR 평가는 평가 척도로만 씁니다. 추천·비추천 수가 PR 상태나 위치를 바꾸지 않고, 머지할 기준값도 없습니다. 앱에서는 머지할 수 없고, 머지는 GitHub PR 페이지에서 사람이 판단해 직접 합니다(머지 조건은 GitHub 리뷰 승인 1명 — Git 전략). 작성자는 비추천 이유를 보고 고치고, 평가 결과와 상관없이 팀 판단으로 PR을 회의실로 끌어갑니다 — 추천이 많아도 더 배울 게 있으면 올리고, 비추천이 많아도 바로 정리되면 올리지 않습니다. 회의에서 "수정 후 재평가"로 정하거나 PR에 새 커밋이 올라오면 평가가 초기화되어 다시 열립니다.

**검토와 판정은 팀원끼리 합니다.** PR을 검토하고 평가하는 일 자체가 동료 학습이라고 보고, 추천·비추천 평가와 회의로 팀원들이 직접 판단합니다. 강사나 AI가 대신 판정하는 역할은 두지 않습니다. 강사는 도움을 요청한 학생에 한해 강사의 시각에서 도움(답변 · 꼬리질문 · 결정 피드백)을 주고, 결정 · 평가 · 안건 · 도움 요청의 상태를 바꾸지 않습니다 (SP3, 2026-10-30 결정). 추천과 비추천 모두 한 줄 이유를 꼭 남겨서 작성자가 무엇이 좋았고 무엇을 고칠지 알 수 있게 하고, 회의에서는 팀원끼리 의견을 조율해 결정과 배운 점을 남깁니다. 앱은 누가 옳은지 판정하지 않고, 평가와 토론과 결정의 흐름만 보여줍니다.

**안건 도형과 상태 표시**

| 안건 종류 | 3D 도형 | 2D 보드 아이콘 |
| --- | --- | --- |
| 이슈 | 정육면체 상자 | ■ |
| PR | 삼각기둥 | ▲ |
| 도움 요청 | 구 | ● |
| 배운 점 공유 | 팔면체(보석 모양) | ◆ |
| 기타 | 납작한 메모지 | 모서리 접힌 메모 |

- 도형은 안건 종류만 나타냅니다. 색은 우선순위에 쓰고, 안건 종류를 색으로 구분하지 않습니다.
- 상태는 도형을 바꾸지 않고 작은 배지·테두리·크기로 표시합니다.
  - PR: 해결 안 된 리뷰 스레드는 말풍선 배지, 병합 충돌은 충돌 배지
  - 이슈: PR 없이 오래 작업 중이면 시계 배지
  - 공통: 오래 방치된 안건은 경고 배지, 지난 회의 결정의 후속 확인은 체크 배지

**개인 학습 타임라인 (본인과 강사만)**

내 PR이 받은 추천·비추천 이유와 회의 결정, 그 뒤에 고친 것, 내가 남긴 평가 이유, 그리고 내가 올린 안건과 그 결론(받은 강사 피드백 포함)을 시간순으로 보여줍니다. 다른 팀원은 볼 수 없습니다. 프로젝트가 끝나면 이 타임라인이 회고 리포트의 기술 결정 카드(FR-REP-07) 재료가 됩니다.

## 회고 리포트와 면접 준비

회고 리포트에는 기술 결정 카드를 더합니다. 카드는 앱이 이미 가진 GitHub 데이터와 평가·회의 기록을 정해진 칸에 규칙대로 옮겨 만듭니다. 이 방식으로 충분하므로 v1에서는 카드 생성에 AI를 붙이지 않고, 필요해지면 그때 검토합니다. 학생이 요청한 카드에는 강사가 꼬리질문을 직접 써서 붙입니다(FR-REP-11). 강사는 모든 카드를 보지만 꼬리질문은 요청된 카드에만 쓰고, AI로 만들지 않으며, 카드 9칸이 아니라 따로 붙는 영역에 둡니다. 면접 꼬리질문 연습은 후순위 기능으로 둡니다. 연습 기능을 붙이더라도 점수 없이 본인과 강사만 봅니다.

| ID | 요구사항 | 수용 기준 | 우선순위 |
| --- | --- | --- | --- |
| FR-REP-07 | 머지되거나 닫힌 내 PR로 기술 결정 카드를 만든다 | 각 칸은 아래 표의 재료를 규칙대로 옮겨 채우고, 재료가 없는 칸은 비워 두며, 본인이 고칠 수 있다 | Must (2026-10-30 올림) |
| FR-REP-08 | 카드마다 예상 면접 질문을 만든다 | 정해진 질문 틀에 카드 내용을 넣어 만든다 (예: 비추천 이유가 있으면 "이 의견을 듣고 무엇을 바꿨나요?") | 후순위 (v1 이후) |
| FR-REP-09 | 질문에 답을 적고 스스로 고쳐 쓴다 | 이전 답변과 나란히 비교할 수 있고, 본인만 쓰며 점수·등급은 없다 (TBD-11) | 후순위 (v1 이후) |
| FR-REP-10 | 카드, 질문, 답변은 본인과 강사만 본다 | FR-REP-06과 TBD-02의 공개 범위를 따른다. 다른 팀원은 볼 수 없다 (2026-10-30 결정) | Must (FR-REP-07 채택 시) |
| FR-REP-11 | 학생이 기술 결정 카드에 강사 꼬리질문을 요청하고 받는다 | 꼬리질문은 요청된 카드에만, 강사가 직접 쓴다(AI 없음). 카드 9칸과 따로 붙는다 | Must (2026-10-30 추가) |

**사용 흐름**

1. 리포트 만들기를 누르면 시작됩니다. 프로젝트 종료 시점이나 1주차 중간 리포트(FR-REP-05)를 만들 때입니다.
2. 내 PR 중 회의 안건이었던 PR, 재평가를 거친 PR, 비추천 이유가 달린 PR 순으로 후보가 올라오고, 본인이 카드로 만들 PR을 고릅니다.
3. PR별로 아래 재료를 시간순으로 모아 칸에 그대로 옮깁니다. 요약하거나 문장을 새로 만들지 않고, 재료가 없는 칸은 비워 둡니다.
4. 본인이 칸을 확인하고 고치며 "내가 배운 점"을 직접 씁니다. 확인하지 않은 카드는 리포트에 넣지 않습니다.
5. 카드에 강사 꼬리질문을 요청할 수 있습니다. 강사가 직접 쓴 꼬리질문은 카드 칸과 따로 붙습니다 (FR-REP-11).
6. 마크다운으로 내보낼 때 팀원 이름은 "팀원 A"처럼 바꿔, 블로그에 올려도 실명이 나가지 않게 합니다 (FR-REP-03).
7. 후순위 기능이 붙으면, 카드별 질문에 답을 적고 이전 답변과 비교하며 다시 씁니다.

**카드 칸과 재료**

| 카드 칸 | 재료 | 출처 |
| --- | --- | --- |
| 무엇을 하려 했나 | 연결된 요구사항 제목, 연결 이슈 본문 | GitHub (명세 문서, 이슈) |
| 처음 택한 방법 | 첫 평가 시점의 PR 본문과 커밋 메시지 | GitHub (PR, 커밋) |
| 받은 평가 | 팀원들의 추천·비추천 이유 (익명) | 앱 서버 (PR 평가) |
| 회의에서 정한 것 | 회의 결정, 배운 점 메모 | 앱 서버 (회의) |
| 최종적으로 바꾼 것 | 회의 이후 커밋 메시지, 변경 파일 목록 | GitHub (커밋) |
| 왜 그렇게 결정했나 | PR 템플릿의 "고민한 점" 항목, 회의 메모 원문 | GitHub (PR), 앱 서버 (회의) |
| 막혔던 순간 | 스탠드업 "막힌 것"에 그 이슈가 언급된 기록 | 앱 서버 (스탠드업) |
| 내가 배운 점 | 본인 직접 입력 | 본인 (FR-REP-02) |
| 원본 | PR, 이슈, 회의록 링크 | GitHub, 앱 서버 |

PR 템플릿에 "고민한 점" 항목을 두면 "왜" 칸이 채워집니다.

점수를 두지 않는 이유는 두 가지입니다. 정의서가 채점을 범위에서 뺐고(1.2), 순위 경쟁은 쪼갠 커밋과 의미 없는 PR을 늘려 면접관이 볼 레포 자체를 망가뜨리기 때문입니다.

강사에게는 화면이 보기 전용으로 열립니다. 학생이 요청한 건에서만 답할 수 있고, 답은 강사 요청함이나 원래 화면(게시판의 도움 요청 · 결정 기록, 회고 리포트의 기술 결정 카드)에서 씁니다. 컨벤션 라이브러리 편집은 언제든 할 수 있습니다 (FR-AUTH-08). 강사는 사무실 열기 · 수집 동의를 거치지 않고, 로그인하면 학생과 같이 마지막에 들어간 사무실로 갑니다. 결정 피드백은 게시판의 결정 기록과 스탠드업·회의 화면 두 곳에서 요청합니다 (2026-10-30 결정).

**진입 흐름**

1. GitHub으로 로그인합니다. 이전에 들어간 사무실이 있으면 마지막 사무실로 바로 갑니다.
2. 조직을 고릅니다. 앱 접근이 허용되지 않은 조직은 잠금 표시와 승인 요청 버튼이 보입니다.
3. 레포를 고릅니다. 레포마다 사무실 열림 여부와 내 역할이 표시됩니다.
   - 팀장(레포 주인)이 열리지 않은 레포를 고르면 사무실을 열고 팀 설정(기간, 명세 문서 경로)을 합니다.
   - 팀원이 열리지 않은 레포를 고르면 안내와 팀장 이름만 보입니다.
   - 열린 사무실에 처음 들어가는 팀원은 활동 기록 수집 동의를 거칩니다.
4. 3D 사무실로 들어갑니다. 한 화면에는 사무실 하나만 보이고, 같은 조직에 등록된 레포가 여럿이면 상단 바의 레포 드롭다운으로 보는 사무실을 바꿉니다. 강사는 같은 드롭다운으로 콜라보레이터인 모든 조의 레포를 오갑니다.

디자인 원칙은 세 가지입니다. 팀원 간 · 조 간 순위·비교 화면은 강사 화면을 포함해 어디에도 두지 않습니다 (FR-FLOW-06). 학습 타임라인과 리포트 같은 개인 지표는 본인과 강사만 봅니다 (NFR-06, 2026-10-30 결정). 막힘 표시는 막혔다는 사실만 보이고 이유나 사람 이름을 붙이지 않아, 감시가 아니라 팀이 함께 볼 신호로 읽히게 합니다.

## 기대 효과 및 향후 확장

오피스는 막힘을 이틀 안에 드러내 2주 일정을 지키게 하고, 프로젝트가 끝났을 때 각자 면접에서 설명할 수 있는 회고 리포트를 남기는 것이 기대 효과입니다.

**기대 효과**

- 팀원: 막혔을 때 먼저 말하지 않아도 사무실에 드러나고, 끝나면 내 기술 결정이 리포트로 남습니다.
- 팀장: 요구사항 진행률과 빈틈을 한눈에 보고, 리뷰 편중을 일찍 조정합니다.
- 레포: 팀 규칙대로 쓰는 습관이 잡혀서, 면접관이 봐도 읽기 좋은 이슈와 PR이 남습니다.

**발표 포인트**

1. 부캠에서는 PR을 두고 의견을 나누고 토론하는 과정 자체가 학습이라는 관점에서 출발한 LMS라는 점
2. 누구나 무엇이든 회의실 안건으로 올려, 팀이 함께 토론하며 배우는 구조
3. 강사는 모든 것을 보되 학생이 요청한 곳에서만 돕는 구조
4. 팀의 작성 방식을 바꾸지 않고 GitHub를 그대로 읽는 구조 (CON-01, CON-02)
5. 점수 대신 흐름을 보여주고, 코드 밖 기여는 팀원 확인으로 기록하는 설계와 그 이유
6. 우리 조가 직접 시범 운영한 데이터와 각자의 학습 타임라인, 회고 리포트로 시연

**향후 확장 (정의서 7장)**

- v2: 한 조직 안에 레포가 여러 개면 레포마다 층을 하나씩 두는 층별 사무실로 늘립니다. 다른 조의 레포는 등록하지 않고, 우리 조직 안의 레포만 층으로 쌓아 층을 오가며 봅니다. GitHub 쓰기 확장도 이때 검토합니다.
- v3 또는 파생작: 회사 개발팀, 스터디 그룹, 사내 온보딩, 오픈소스 멘토링, GitLab·Jira 어댑터
- 면접 준비: 기술 결정 카드 기반 꼬리질문 연습(FR-REP-08\~10), 동료 모의 면접, 기수 단위 질문 모음 (공개 범위 결정 후)
