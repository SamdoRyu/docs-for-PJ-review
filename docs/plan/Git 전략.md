# Git 전략

> 문서 상태: 팀 협의용 초안  
> 적용 대상: 프로젝트 전체 팀원  
> 적용 시점: 팀 합의 및 GitHub 설정 완료 후

## 1. 개요와 운영 원칙

4인 팀이 2주 동안 한 레포에서 서로 덮어쓰지 않고 일하고, 이슈 → 브랜치 → PR → 머지를 요구사항 정의서 ID로 추적하기 위한 규칙입니다.

- 모든 작업은 이슈에서 시작합니다. 이슈 하나당 브랜치 하나, PR 하나입니다.
- `main`과 `develop`에는 직접 push하지 않고 PR로만 합칩니다.
- 이슈와 PR에 요구사항 정의서 ID를 적어 설계·개발·테스트를 ID로 추적합니다.
- **결정 필요**는 팀이 아직 정하지 않은 항목이고, **설정 필요**는 GitHub에 아직 적용되지 않은 설정입니다. 두 가지 모두 「9. 팀 협의 및 설정이 필요한 사항」에 모았습니다.
- 앱의 컨벤션 규칙 설정(FR-HAB-10, 검토 중)이 채택되면 이 문서의 패턴을 그대로 등록해, 개발 중인 우리 레포를 첫 검사 대상으로 씁니다.

## 2. 브랜치 전략

`main`은 시연·배포용, `develop`은 통합용입니다. 작업 브랜치는 최신 `develop`에서 만들어 PR로 합칩니다.

```text
작업 브랜치 ──(이슈 PR · squash merge)──────▶ develop
develop    ──(승격 PR · merge commit)───────▶ main
hotfix     ──(hotfix PR · squash merge)─────▶ main ──(동기화 PR · merge commit)──▶ develop
```

| 브랜치 | 이름 | 만드는 곳 | 합치는 곳 | 합치는 방식 |
| --- | --- | --- | --- | --- |
| 배포 | `main` | 레포 기본 브랜치 | 승격 PR과 hotfix PR만 받음 | — |
| 통합 | `develop` | `main`에서 1일차에 한 번 | 이슈 PR을 받음 | — |
| 작업 | `<type>/<이슈번호>-<slug>` | 최신 `develop` | `develop` | squash merge |
| 긴급 수정 | `hotfix/<이슈번호>-<slug>` | `main` | `main`, 이어서 `main` → `develop` 동기화 | hotfix PR은 squash merge, 동기화는 merge commit |

**규칙**

- `develop`에서도 직접 개발하지 않습니다. 모든 변경은 작업 브랜치에서 합니다.
- `main`과 `develop`에는 직접 push와 force push를 하지 않습니다. 남의 브랜치도 force push하지 않습니다.
- 승격 PR과 동기화 PR은 squash하지 않고 merge commit으로 합칩니다. squash하면 두 브랜치의 이력이 어긋나 다음 승격 때 이미 합친 변경이 다시 diff에 잡힙니다.
- 머지된 브랜치는 바로 삭제합니다.

**main 승격 일정** (결정 필요)

기획안 일정 기준으로 7일차 1차 데모, 10일차 기능 동결, 12일차 시연 영상 촬영, 14일차 발표 직전, 이렇게 네 번 승격할 계획입니다. 팀 일정이 확정되면 이 날짜를 고칩니다.

> **현재 상태 (2026-10-28 확인)**: 템플릿을 둔 레포(`SamdoRyu/docs-for-PJ-review`)에는 `main`만 있고 `develop`은 아직 없습니다. 브랜치 보호 규칙도 없습니다. 팀 개발 레포가 따로 있으면 그 레포에서 다시 확인합니다. → 「9」 GitHub 설정

## 3. 브랜치 이름 규칙

형식은 `<type>/<이슈번호>-<slug>`입니다.

- type은 `feat`, `fix`, `refactor`, `test`, `docs`, `chore`, `hotfix` 중 하나이고, 이슈의 종류 라벨을 따릅니다.

  | 이슈 종류 라벨 | 브랜치 type |
  | --- | --- |
  | `feature` | `feat` |
  | `bug` | `fix` (시연 직전 `main` 긴급 수정은 `hotfix`) |
  | `chore` | `chore`, `refactor`, `test`, `docs` 중 맞는 것 |

- 이슈번호는 GitHub 이슈 번호를 숫자로만 씁니다. `#`은 붙이지 않습니다.
- slug는 짧은 영문 소문자 kebab-case로, 3단어 이내로 씁니다.

**예시**

| 브랜치 이름 | 판정 | 이유 |
| --- | --- | --- |
| `feat/12-github-login` | 맞음 | |
| `fix/18-login-fix` | 맞음 | |
| `hotfix/40-demo-crash` | 맞음 | |
| `fix/#18-login-fix` | 틀림 | 이슈번호에 `#`을 붙임 |
| `login-fix` | 틀림 | type과 이슈번호가 없음 |
| `feat/12-GitHub_Login` | 틀림 | 대문자와 밑줄을 씀 |
| `feature/12-github-login` | 틀림 | `feature`는 라벨 이름이고 브랜치 type은 `feat` |

앱의 브랜치 이름 검사(FR-HAB-08, 검토 중)가 채택되면 아래 패턴을 등록합니다. 패턴은 slug의 단어 수까지는 검사하지 않습니다.

```text
^(feat|fix|refactor|test|docs|chore|hotfix)/[0-9]+-[a-z0-9]+(-[a-z0-9]+)*$
```

> **결정 필요**: 기획안 「협업 컨벤션 피드백」의 고친 예시는 `fix/#18-login-fix`처럼 `#`을 붙입니다. 이 문서는 `#` 없는 `fix/18-login-fix`를 씁니다. `#`은 URL에서 따로 인코딩해야 해서 브랜치 링크가 깨지기 쉽기 때문입니다. 팀이 한쪽으로 정한 뒤 FR-HAB-08 패턴과 기획안 예시를 같이 맞춥니다.

## 4. 커밋 메시지 규칙

커밋은 Conventional Commits 형식 `<type>(<scope>): <설명>`으로 씁니다. `(<scope>)`는 선택입니다.

| type | 언제 |
| --- | --- |
| `feat` | 사용자가 쓰는 기능 추가 |
| `fix` | 버그 수정 |
| `refactor` | 동작은 그대로, 구조만 바꿈 |
| `perf` | 성능 개선 |
| `test` | 테스트 추가·수정 |
| `docs` | 문서만 바꿈 |
| `style` | 포맷·세미콜론 등 동작과 무관한 변경 |
| `build` | 빌드 설정, 의존성 |
| `ci` | CI 설정 |
| `chore` | 그 밖의 잡일 |

**규칙**

- 설명은 50자 이내로 쓰고, 한국어로 써도 되며 끝에 마침표를 찍지 않습니다.
- 범위를 밝히고 싶으면 `feat(sync): …`처럼 괄호에 영역을 적습니다. 영역 이름은 라벨의 `area:` 뒤 값과 같게 씁니다 (`auth`, `sync`, `req`, `office`, `flow`, `vote`, `habit`, `meeting`, `plan`, `report`).
- 본문은 필요할 때만 쓰고, "무엇을"보다 "왜"를 적습니다.
- 한 커밋에 한 가지 변경만 담습니다.

**브랜치 type과 커밋 type은 다릅니다**

- 브랜치 type은 이슈 종류로 하나 정해지고, 커밋 type은 커밋마다 내용에 맞게 고릅니다. 예를 들어 `chore/31-ci-setup` 브랜치에 `ci: …` 커밋이 들어갈 수 있습니다.
- `hotfix`는 브랜치 type일 뿐 커밋 type이 아닙니다. hotfix PR의 제목은 `fix: …`로 씁니다.

**PR 제목이 develop의 커밋이 됩니다**

이슈 PR은 squash merge하므로 작업 브랜치 안의 커밋들은 하나로 합쳐지고, **develop에 남는 커밋 제목은 PR 제목**입니다. GitHub은 squash 커밋 제목 끝에 `(#PR번호)`를 붙입니다. 그래서 PR 제목은 반드시 이 커밋 형식으로 씁니다. 작업 브랜치 안의 커밋도 같은 형식으로 씁니다.

**예시**

```text
feat(sync): 레포 변경분 5분 폴링 추가
fix(vote): 작성자 본인 투표가 저장되던 문제 수정
docs: 환경 변수 가이드에 GitHub App 설정 추가
feat(sync): 레포 변경분 5분 폴링 추가 (#24)    ← squash merge 후 develop에 남는 모습
```

앱의 커밋 규칙 검사(FR-HAB-04)에는 아래 패턴을 등록합니다. 패턴은 커밋 메시지의 첫 줄(제목)에만 적용하고, `: ` 뒤 설명이 1\~50자인지 봅니다. 마침표 금지는 패턴으로 검사하지 않습니다.

```text
^(feat|fix|refactor|perf|test|docs|style|build|ci|chore)(\([a-z0-9-]+\))?: .{1,50}$
```

> **결정 필요**: 기획안 「협업 컨벤션 피드백」의 검사 대상 표는 PR 제목을 `[type] 설명` 형식으로 적었습니다. 이 문서는 PR 제목이 그대로 develop 커밋이 되므로 커밋과 같은 Conventional Commits 형식을 씁니다. `[type] 설명`을 택하면 위 커밋 패턴과 충돌하므로 팀이 한쪽으로 정합니다.

## 5. Issue 작성 규칙

모든 작업은 이슈에서 시작합니다. GitHub에서 New issue를 누르면 아래 세 템플릿 중 하나를 고르게 되고, 빈 이슈는 만들 수 없습니다 (`.github/ISSUE_TEMPLATE/config.yml`의 `blank_issues_enabled: false`).

| 템플릿 | 언제 | 제목 앞머리 | 자동 라벨 | 필수 칸 | 선택 칸 |
| --- | --- | --- | --- | --- | --- |
| Feature | 새 기능, 사용자 가치 추가 | `[Feature]` | `feature` | 요구사항 ID, 문제 / 목적, 완료 조건 | 범위 메모, 참고 |
| Bug | 재현 가능한 잘못된 동작 | `[Bug]` | `bug` | 현상(실제 / 기대), 재현 절차 | 요구사항 ID, 환경 · 로그 · 스크린샷 |
| Task / Chore | 리팩터링, 설정, 문서, 테스트, 유지보수 | `[Task]` | `chore` | 요구사항 ID, 목표 | 작업 항목 |

**작성 방법**

- **제목**: 앞머리는 템플릿이 붙입니다. 뒤에 결과를 한 줄로 씁니다. 예: `[Feature] 레포 변경분 폴링 동기화`
- **요구사항 ID**: 요구사항 정의서의 ID를 적고, 여러 개면 쉼표로 구분합니다. 예: `FR-GH-03, NFR-10`. 설정 작업처럼 해당 ID가 없으면 "없음"이라고 씁니다.
- **완료 조건**(Feature): 끝났는지 판단할 기준을 체크리스트로 씁니다. `docs/04-features.md`의 「인수 조건」을 그대로 옮겨도 됩니다.
- **목표**(Task): 무엇을 하면 끝나는지 한두 줄로 씁니다.
- **재현 절차**(Bug): 재현이 안 되면 언제·어디서 봤는지라도 적습니다. 로그와 스크린샷에서 secret과 개인정보는 지웁니다.
- **라벨**: 종류 라벨은 템플릿이 붙입니다. 영역 라벨(`area:*`)은 템플릿이 붙이지 않으므로 직접 하나 붙입니다. → 「8. 라벨 관리」
- **크기**: 이슈 하나는 1\~2일 안에 끝낼 크기로 나눕니다. 넘으면 하위 이슈로 쪼갭니다.
- **담당자**: 작업을 시작할 때 지정합니다. 우리 앱에서는 담당자 지정이 곧 상자가 내 책상으로 옮겨지는 것입니다 (FR-OFF-02).

> **설정 필요**: 템플릿의 자동 라벨은 레포에 같은 이름의 라벨이 있어야 붙습니다. 지금은 `bug`만 있고 `feature`와 `chore`는 없어서 Feature·Task 이슈에는 라벨이 붙지 않습니다.

## 6. PR 작성 규칙

**base 브랜치**

| PR 종류 | base | 본문의 이슈 연결 |
| --- | --- | --- |
| 이슈 PR | `develop` | `Refs #N` |
| develop → main 승격 PR | `main` | 포함된 이슈를 `Closes #N`으로 한 줄씩 나열 |
| hotfix PR | `main` | 결정 필요 |
| main → develop 동기화 PR | `develop` | — |

- GitHub 기본 base가 `main`이라 PR을 만들 때 base를 꼭 확인합니다.
- GitHub은 기본 브랜치(`main`)로 머지되는 PR의 `Closes #N`만 이슈를 닫습니다. 그래서 develop 대상 PR은 `Refs #N`으로 참조만 남기고, 이슈는 main 승격 PR이 닫습니다.

> **FR-HAB-01과의 관계**: 앱의 연결 이슈 검사(FR-HAB-01)가 `Refs #N`도 연결로 인정하는 것은 아직 검토 중인 수정안입니다. 수정안이 채택되기 전에 FR-HAB-01을 구현하면 develop 대상 PR이 모두 "연결 이슈 없음"으로 잡힐 수 있습니다. 위 Git 규칙(`Refs #N` 사용)은 그대로 지키고, 수정안 채택 여부는 팀이 FR-HAB-01 구현 전에 정합니다.

**제목**

커밋 메시지와 같은 형식입니다. squash merge 후 그대로 develop의 커밋이 됩니다. 예: `feat(sync): 레포 변경분 5분 폴링 추가` → 「4. 커밋 메시지 규칙」

**크기**

변경이 400줄을 넘으면 나눕니다. 앱의 PR 크기 안내(FR-HAB-07) 기준도 400줄로 맞춥니다.

**본문**

`.github/PULL_REQUEST_TEMPLATE.md`의 칸을 채웁니다.

| 섹션 | 쓰는 것 |
| --- | --- |
| 무엇을 · 왜 | 무엇을 바꿨고 왜 필요한지 2\~4줄. 주요 변경이 여러 개면 목록으로 |
| 관련 Issue | `Refs #N` (승격 PR은 `Closes #N`) |
| 관련 요구사항 | 요구사항 정의서 ID. 이슈에 적은 것과 같게 |
| 고민한 점 | 검토한 대안과 이 방법을 고른 이유. 대안을 따로 검토하지 않았으면 "없음". 회고 리포트의 기술 결정 카드(FR-REP-07, 검토 중)로 옮겨질 재료입니다 |
| 검증 | 실제로 돌린 명령, 확인한 시나리오와 결과. 못 한 것은 못 했다고 적습니다. CI가 placeholder인 동안 CI 통과는 검증으로 세지 않습니다 |
| UI 변경 | 화면이 바뀌었으면 스크린샷이나 GIF, 아니면 "해당 없음" |
| 영향 범위 / 위험 | `GitHub 권한·API 호출량 변경: 없음 / 있음` 중 하나를 남깁니다. API, DB schema, 환경 변수, dependency 변경, 보안 영향, 기존 기능 회귀 가능성이 있으면 적고 없으면 비워 둡니다. 마지막으로 "secret · 개인정보 · 디버그용 임시 코드가 없다"를 확인해 체크합니다 |

## 7. 코드 리뷰 및 머지 규칙

머지 조건은 **앱의 PR 찬성·반대 투표 기능을 쓰기 전과 후**로 나뉩니다. 지금은 "사용 전" 규칙을 따릅니다.

### 지금: 앱의 투표 기능을 쓰기 전

| 머지 조건 | 머지 방식 | 의견이 갈리면 |
| --- | --- | --- |
| GitHub 리뷰 승인 2명, 그리고 리뷰어가 PR 「검증」에 적힌 실제 명령과 결과를 확인 | 이슈 PR은 squash merge | 다음 날 스탠드업에서 안건으로 다룸 |

- **CI는 아직 검증이 아닙니다.** 지금 `.github/workflows/ci.yml`은 lint·test·build 대신 `echo` 한 줄만 돌려서 항상 통과합니다. CI 초록 표시를 검증으로 세지 않고, 리뷰어가 「검증」 칸을 직접 확인합니다.
- 스택이 정해져 CI에 실제 lint·test·build 단계가 들어가면 "CI 통과"를 머지 조건에 더합니다.
- 브랜치 보호 규칙이 켜지기 전까지 "승인 2명"은 GitHub이 막아 주지 않는 팀 약속입니다. 머지하는 사람이 승인 수를 직접 확인합니다. → 「9」 GitHub 설정

### 예정: 앱의 투표 기능을 쓰게 된 뒤

아래 세 가지가 모두 갖춰지기 전까지는 위의 "지금" 규칙을 따릅니다.

1. 팀이 PR 투표 요구사항(FR-LRN-01\~03)을 채택한다 (지금은 검토 중).
2. 투표 기능이 구현되고, 우리 레포에서 실제로 동작하는지 확인한다.
3. 팀이 전환 시점을 합의한다.

| 머지 조건 | 머지 방식 | 의견이 갈리면 |
| --- | --- | --- |
| (CI에 실제 단계가 있으면) CI 통과, 그리고 앱에서 찬성 2표 이상·반대 0표 → 작성자가 GitHub에서 merge | 이슈 PR은 squash merge | 투표와 상관없이 누구나 PR을 회의실 안건으로 올려 회의 |

- **결정 필요**: 전환 뒤 GitHub 필수 승인 수를 어떻게 할지 정합니다. 기획안 「리스크 및 대응 방안」은 앱 투표를 공식 결정으로 삼고, GitHub 승인은 브랜치 보호 규칙이 있을 때만 쓰자고 했습니다. 보호 규칙에 필수 승인 2명을 걸어 둔 채 전환하면 같은 판단을 두 번 하게 됩니다.
- **결정 필요**: PR에 새 커밋이 올라왔을 때 기존 투표를 어떻게 할지, 회의에서 "그대로 머지"로 정한 PR에 반대표가 남아 있을 때 어느 쪽을 따를지는 아직 정하지 않았습니다 (`docs/05-policy.md` P7).

### 시기와 상관없이

- 리뷰 요청을 받으면 12시간 안에 첫 의견을 남깁니다. 막힘 기준 기본값(리뷰 대기 12시간, TBD-05)과 같습니다.
- 반대나 변경 요청에는 PR 내용에 대한 이유를 한 줄 이상 남깁니다.
- 이슈 PR과 hotfix PR은 squash merge, develop → main 승격과 main → develop 동기화는 merge commit으로 합칩니다.

## 8. 라벨 관리

이슈에는 종류 라벨 하나와 영역 라벨 하나를 붙입니다. 종류 라벨은 템플릿이 자동으로 붙이고 브랜치 type을 정합니다. 영역 라벨은 직접 붙이고, 커밋 scope에도 같은 값을 씁니다. 라벨 정의는 `.github/labels.yml`에 있습니다.

| 종류 라벨 | 붙는 곳 | 브랜치 type |
| --- | --- | --- |
| `feature` | Feature 템플릿 | `feat` |
| `bug` | Bug 템플릿 | `fix` (시연 직전 긴급 수정은 `hotfix`) |
| `chore` | Task 템플릿 | `chore`, `refactor`, `test`, `docs` 중 맞는 것 |

영역 라벨은 기술 스택이 아니라 **기능 영역**입니다. 요구사항 정의서의 기능 그룹과 1:1로 맞춥니다.

| 영역 라벨 | 기능 영역 (정의서 기능 그룹) |
| --- | --- |
| `area:auth` | 계정·권한 (FR-AUTH) |
| `area:sync` | GitHub 연동 (FR-GH) |
| `area:req` | 요구사항 추적 (FR-REQ) |
| `area:office` | 3D 사무실 (FR-OFF) |
| `area:flow` | 진행·막힘 (FR-FLOW) |
| `area:vote` | PR 투표와 회의실 학습 (FR-LRN, 제안) |
| `area:habit` | 협업 기본기·컨벤션 피드백 (FR-HAB) |
| `area:meeting` | 회의·스탠드업 (FR-MTG) |
| `area:plan` | 일정판 (FR-PLAN) |
| `area:report` | 회고 리포트 (FR-REP) |

- 영역 라벨은 개인 회고 리포트(FR-REP-01)에 모여 "내가 어떤 기능 영역을 맡았나"를 보여 줍니다. 리포트에서 이 항목을 부르는 이름("다룬 기술" 또는 "담당 기능 영역")은 검토 중입니다 (`docs/requirements-changes.md` 「6. 우선순위 검토 메모」).

> **설정 필요**: `.github/labels.yml`은 정의 파일일 뿐이라 GitHub에 자동으로 반영되지 않습니다. 지금 레포에는 GitHub 기본 라벨만 있고, 정의 파일과 같은 이름은 `bug` 하나뿐입니다. `feature`, `chore`, `area:*` 10개는 GitHub 라벨 화면에서 같은 이름으로 만들어야 합니다.

## 9. 팀 협의 및 설정이 필요한 사항

### 팀이 정할 것

| # | 항목 | 이 문서의 현재 안 | 참고 |
| --- | --- | --- | --- |
| 1 | 브랜치 이름에 `#`을 붙이는가 | 붙이지 않음 (`fix/18-login-fix`) | 기획안 예시 `fix/#18-login-fix`, FR-HAB-08 |
| 2 | PR 제목 형식 | Conventional Commits (`feat(sync): …`) | 기획안 검사 대상 표 `[type] 설명`, FR-HAB-08 |
| 3 | PR 템플릿 파일 이름 대소문자 | `.github/PULL_REQUEST_TEMPLATE.md` | 기획안 `.github/pull_request_template.md`, FR-HAB-02 |
| 4 | main 승격 일정 | 기획안 기준 7·10·12·14일차 | 팀 일정 |
| 5 | 앱 투표로 머지 규칙을 바꿀지, 바꾼다면 언제 | 바꾸기 전 규칙 적용 | FR-LRN-01\~03 검토 중, 7일차 데모 범위와 연결 |
| 6 | 투표 전환 뒤 GitHub 필수 승인 수 | 정하지 않음 | 기획안 「리스크 및 대응 방안」 |
| 7 | 새 커밋 뒤 투표 처리, "그대로 머지"와 반대표 중 우선순위 | 정하지 않음 | `docs/05-policy.md` P7, FR-LRN-05·06 |
| 8 | FR-HAB-01이 `Refs #N`을 연결로 인정하는 수정안 채택 시점 | Git 규칙은 `Refs #N` 사용 | `docs/requirements-changes.md` 2절·6절 |
| 9 | hotfix PR의 이슈 연결 키워드 (`Refs` 또는 `Closes`) | 정하지 않음 | — |
| 10 | 승격·동기화 merge commit 메시지(`Merge pull request …`)를 커밋 규칙 검사에서 뺄지 | 정하지 않음 | FR-HAB-04 패턴과 맞지 않음 |
| 11 | 이슈에 요구사항 ID를 적는 위치 | 템플릿의 「요구사항 ID」 칸 | 기획안 「개발 원칙」은 "이슈 제목이나 라벨" |
| 12 | 회고 리포트에서 영역 라벨을 부르는 이름 | 기능 영역 | FR-REP-01, `docs/requirements-changes.md` 6절 |
| 13 | GitHub 기본 라벨(`enhancement`, `documentation` 등)을 지울지 | 정하지 않음 | 종류 라벨과 헷갈릴 수 있음 |

### GitHub에서 설정할 것

아래 "현재 상태"는 2026-10-28에 템플릿을 둔 레포(`SamdoRyu/docs-for-PJ-review`)에서 읽기 전용으로 확인한 내용입니다. 팀 개발 레포가 따로 있으면 그 레포에서 다시 확인하고, `.github/` 템플릿과 워크플로도 그 레포에 같이 옮깁니다.

| 설정 | 현재 상태 | 할 일 |
| --- | --- | --- |
| `develop` 브랜치 | 없음 (`main`만 있음) | `main`에서 만든다 |
| `main` 보호 규칙 | 없음 (ruleset도 없음) | PR 필수, 직접 push·force push·삭제 금지 |
| `develop` 보호 규칙 | 브랜치 없음 | PR 필수, 직접 push·force push·삭제 금지, 필수 승인 2명 (투표 전환 전 규칙 기준) |
| 머지 방식 | squash, merge commit, rebase 모두 허용 | rebase merge를 끈다. squash(이슈 PR)와 merge commit(승격·동기화)은 둘 다 필요하므로 머지할 때 방식을 확인한다 |
| 머지 후 브랜치 자동 삭제 | 꺼짐 | Automatically delete head branches를 켠다 |
| 라벨 | GitHub 기본 라벨만 있음 (`bug`만 일치) | `.github/labels.yml`대로 `feature`, `chore`, `area:*` 10개를 만든다 |
| CI | placeholder (`echo` 한 줄, 항상 통과) | 스택이 정해지면 lint·test·build 단계를 채우고, 그 뒤 보호 규칙의 필수 status check로 등록한다 |
| 빈 이슈 차단 | 적용됨 (`config.yml`) | 개발 레포에도 같은 파일을 둔다 |
