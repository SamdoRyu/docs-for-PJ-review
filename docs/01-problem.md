## 4요소

| 칸        | 내용                                                                                                                              |
| -------- | ------------------------------------------------------------------------------------------------------------------------------- |
| **문제**   | 부캠 팀 프로젝트는 **2주** 안에 끝나서 막힘이 하루만 방치돼도 일정이 무너지고, 끝난 뒤에는 배운 것이 이슈와 PR에 흩어진 채 면접 직전까지 정리되지 않는다. |
| **대상**   | **부캠 19명, 5개 조 중 우리 조 하나**의 4인 팀 — 참여자(팀원, ROLE-01)와 레포 관리자(팀장, ROLE-02) · ASM-01, ASM-02 |
| **현재해법** | GitHub의 이슈 · PR · 코멘트로 일하고, 누가 리뷰를 기다리는지와 어떤 이슈가 멈췄는지는 목록을 하나씩 열어 확인한다. |
| **불편**   | PR이나 이슈에 대한 의견이 GitHub 코멘트 안에 묻혀 **팀이 함께 짚고 넘어가며 배울 자리가 없다**. 명세 문서의 요구사항과 실제 이슈·PR이 연결되지 않아 빠진 요구사항이 마감 직전에 발견된다. 기획, 자료조사, 발표 준비처럼 코드로 남지 않는 기여는 기록되지 않고, 회고 문화가 없어서(ASM-06) 내가 내린 기술 결정과 그 이유를 면접에서 깊이 설명하기 어렵다. |

## 한 문단으로

2주짜리 부캠 팀 프로젝트를 하는 4인 팀은 GitHub의 이슈와 PR로 일하지만, PR을 두고 나온 의견은 코멘트 안에 묻혀 팀이 함께 배울 자리가 없고, 누가 막혔는지는 목록을 하나씩 열어봐야 알 수 있으며, 프로젝트가 끝나면 배운 것과 내가 내린 기술 결정이 정리되지 않은 채 흩어진다. **팀 레포를 그대로 읽어 3D 사무실로 보여 주고, PR · 이슈 · 도움 요청 · 배운 점 무엇이든 회의실 안건으로 올려 함께 토론하는 과정 자체를 학습으로 만들며, 막힘은 먼저 드러나고 배운 것은 면접에서 쓸 수 있는 글로 남게 할 창구가 필요하다.**

| ---------- | ------------- | ------------------------------ |

## 핵심 차별점 — 일은 GitHub, 정리는 앱

활동량이 아니라 **흐름**을 보여주고, 점수 · 순위 · 채점은 두지 않는다. 앱은 GitHub를 **읽기만** 하고(CON-02), 토론 · 투표 · 결정 · 배운 점처럼 GitHub에 없는 것만 앱에 남긴다.

| 회의실 안건 종류 | 출처 | 일 · 배움 |
| -------------- | -------- | -------------- |
| **이슈** | GitHub | 일 |
| **PR** | GitHub | 일 |
| **도움 요청** | 앱 | 배움 |
| **배운 점 공유** | 앱 | 배움 |
| **기타** | 앱 | 배움 |

PR 찬성 · 반대 투표는 머지 여부만 정하는 별도 장치이고, **검토와 판정은 팀원끼리 한다** — 강사나 AI가 대신 판정하지 않는다.

이를 통해 PR을 두고 의견을 나누고 토론하는 과정 자체를 부캠의 학습으로 만든다.

> **기획 의도와 채택 상태는 다르다.** 회의실 안건 5종과 PR 찬성 · 반대 투표는 기획안이 내세우는 핵심 차별점이지만, 이를 만드는 요구사항(FR-LRN-01~14)은 기획안이 정의서에 더한 **[제안]**이고 requirements-changes.md 상태가 "검토 중"이다. 정의서 범위 안에서 확정된 것은 회의실에서 안건을 다루고 결정 · 배운 점을 기록하는 FR-MTG-03 · 04다. "AI · 강사 판정 제외"도 requirements-changes.md 「범위」에서 검토 중이다.

## MVP 핵심 워크플로우

팀 오피스의 흐름은 네 단계다. 각 단계는 02-workflow.md 의 S0~S6 과 대응하며, 여기서는 흐름 이름과 한 줄 설명만 둔다 — 화면·기능 세부는 02~07 문서에서 다룬다. [제안]이 붙은 부분은 requirements-changes.md에서 "검토 중"인 요구사항에 기대고, 팀이 채택하기 전에는 확정 MVP가 아니다.

### 1. 사무실 열기 (S0 · S1)

팀장이 GitHub로 로그인해 우리 조 레포를 고르고 기간과 명세 문서 경로(건너뛸 수 있음)를 넣으면, 첫 동기화 뒤 팀원 책상과 요구사항 구역이 생긴다.

### 2. 일의 흐름 (S2)

이슈 상자가 상태에 따라 사무실 안을 옮겨 다니고, 요구사항 구역별 진행률과 빈 구역, 이유가 붙은 막힘이 보인다.

### 3. 배움의 흐름 (S3 · S4 · S5)

매일 스탠드업을 남기고, 회의실에서 막힌 이슈와 안건을 다뤄 결정과 배운 점을 기록한다(FR-MTG-01~04). PR 본문 · 커밋 · [제안] 브랜치가 팀 규칙대로인지 검사되어 어긴 본인에게만 보인다(FR-HAB). [제안] PR마다 찬성 · 반대 투표가 열리고, 누구나 무엇이든 회의실 안건으로 올려 토론한다(FR-LRN).

### 4. 회고 리포트 (S6)

프로젝트가 끝나면 각자 회고 리포트를 만들고 배운 점을 써서 마크다운으로 내보낸다(FR-REP-01~03). [제안] 기술 결정 카드(FR-REP-07)와 학습 타임라인(FR-LRN-08)은 제안 우선순위가 Should다.

### 흐름 앞뒤의 진입 · 설정 흐름

* **로그인 · 조직·레포 선택 (S0의 앞부분)** — GitHub로 로그인하고 조직과 레포를 고른다. 이전에 들어간 사무실이 있으면 마지막 사무실로 바로 간다. 위 1번 "사무실 열기"는 같은 S0 안에서 팀장이 열리지 않은 레포를 골랐을 때 이어진다. [제안] 팀원은 열린 사무실에 처음 들어갈 때 활동 기록 수집 동의를 거친다 — 수집 동의는 FR-ACT에만 기대므로 FR-ACT가 채택되지 않으면 이 단계도 없다.
* **설정** — 별도 흐름이 없다. 팀장의 팀 설정(기간, 명세 문서 경로, 기준값, [제안] 앱 컨벤션 규칙)은 S0 사무실 열기와 레포 관리자(ROLE-02) 권한에 포함된다(05-policy.md P2).

## 대상 환경

**웹 서비스**이고 **1024px 이상 노트북 · 태블릿**에서 쓴다(NFR-07). 기존 3D 팀 오피스 위에 구축하며(CON-05), 상단 바와 패널이 3D보다 먼저 뜬다(NFR-02). 모바일 반응형은 v1 범위가 아니다.

## MVP 개발 제약 사항

* **점수 · 순위 · 채점 금지**

  * 팀원 간 순위 · 비교 화면과 사람별 활동량 합계 없음 (FR-FLOW-06)
  * 사람별 투표 합계 없음 ([제안] FR-LRN-09 — 투표 기능이 채택될 때 함께 지킨다)
  * 개인 지표는 본인 화면에만 (NFR-06)

* **GitHub 쓰기 금지**

  * 앱은 GitHub를 읽기만 한다 (CON-02)
  * 이슈 만들기와 머지는 GitHub 화면 링크로 (TBD-04 결정 전까지)
  * 웹훅 없이 폴링 (CON-03)

* **범위 밖**

  * 강사 · 운영진 전용 기능, 팀 간 비교, 다른 조 레포 연결
  * 리뷰 판정을 강사나 AI에게 맡기는 구조 (requirements-changes.md 「범위」 검토 중)
  * 출석 · 공지 · 자료실, 일반 배포 서비스 운영 — "공지"는 기획안의 공용 게시 공간에도 있어 결정 필요 (requirements-changes.md 「범위」)
  * 여러 레포를 한 건물로 쌓는 층별 사무실(v2). v1에 등록할 수 있는 레포 수(1개 또는 조직 안 여러 개)는 결정 필요이고, 한 화면에는 항상 사무실 하나만 보인다

## 프로젝트 한 줄 정의
