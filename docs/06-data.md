## 기존 데모 데이터와의 대응

기존 3D 데모(`SamdoRyu/warehouseDemo_fork`)의 `src/data/types.ts`를 읽어 정리했다(2026-10-28). 데모는 **앱 안에서 작업을 만들고 고치는** 팀 관리 대시보드라, GitHub를 읽기만 하는 v1과 데이터의 출처가 다르다. 아래 "v1 출처"는 다음 넷 중 하나다.

- **GitHub 원본** — GitHub에서 읽어 앱 모델로 바꿔 저장(`syncedAt`)
- **앱 저장** — 앱 서버에만 저장
- **계산** — 저장하지 않고 계산
- **[?]** — 출처가 정해지지 않음. 정하지 않고 열린 질문으로 둔다

필드를 확정하는 표가 아니다. 기존 필드가 v1에서 어디서 올 수 있는지만 적었다.

> 작업 필드는 새로 기획 예정(2026-10-28 추가 결정). 우선순위(`priority`) · 포인트(`estimate`) · 마감(`dueDate`) · 담당 여러 명 · `projectId` · 팀원 `capacity` 행은 이 표에서 뺐다. 2026-11-01 결정으로 우선순위는 GitHub `priority:*` 라벨(없으면 중립), 마감은 앱 저장(위 「작업 마감」)으로 정했다. 포인트 · 용량 · `projectId`는 계속 쓰지 않는다(사람별 비교 금지 — FR-FLOW-06).

### 기존 데모에 없는 v1 항목

`GithubIssue` · `GithubPullRequest`(어댑터 DTO — 저장하지 않음), `Submission`(PR) · `SubmissionIssueLink`(PR–이슈 연결) · `SubmissionCommit`(PR 커밋), `Requirement` · `RequirementLink`, 동기화 상태(`SyncState`), `Standup`, 회의 안건(`AgendaItem`) · 강사 피드백(`InstructorFeedback`), 컨벤션 라이브러리 항목(`ConventionLibraryItem`), `RetroReport`, `Evaluation` · PR 평가 회차(`EvaluationRound`) · 도움 요청(`HelpRequest` · `HelpComment`) · `DecisionCard` · 꼬리질문(`FollowUpQuestion`) · 활동 기록(`ActivityRecord` · `ActivityConfirmation`) · 동료 피드백(`PeerFeedback`) · 작업 마감(`TaskDueDate`) · 이슈 담당자(다대다 — `TaskAssignee`) · 사무실(`Workspace`) · 강사 지정(`InstructorAssignment`) · 앱 사용자(`AppUser`) · 승인된 강사 계정(서버 설정) · 심사용 계정(`ReviewAccount`)은 모두 신규다(코드 이름은 GRAVIT main `6a65d1f` 기준). 칸은 위 「저장 항목」 표를 따른다.

> 저장 방식: 데모 서버는 SQLite 테이블마다 `(id, data)` 두 칸에 엔티티 전체를 JSON 문자열로 넣는다. 2026-10-28에는 이 방식을 이어 쓰기로 했지만, 2026-11-01 결정으로 백엔드를 Spring Boot + Spring Data JPA로 새로 만들어 **이 방식은 쓰지 않는다** — 항목마다 JPA Entity와 연관관계로 저장한다(ARCHITECTURE.md 「저장소 (JPA)」 · CONTRACTS.md). 데모의 저장 코드는 참고만 한다.

## 비기능 한 줄

앱은 GitHub를 읽기만 하므로 요구사항 연결 · 회의 기록 · 평가 · 도움 요청 · 활동 기록 · 동료 피드백처럼 앱이 만든 값은 모두 앱 서버에만 저장한다(CON-02 · P3). 시각은 UTC로 저장하고 UTC로 응답하며, 한국 시간 변환은 화면에서 한다(코드 컨벤션 BE). GitHub에서 온 값은 `syncedAt`을 함께 저장하고, 동기화가 실패해도 마지막 데이터를 유지한다(NFR-09 · P4).

> 개인 지표(회고 리포트, 학습 타임라인 · 카드)는 응답 DTO에서 본인과 강사의 요청에만 담는다(NFR-06 · P5 · 2026-10-30 결정 — 습관 체크는 삭제). 사람별 평가 합계, 활동량 합계 같은 칸은 저장 항목에도 응답에도 두지 않는다 — 칸이 없으면 화면에서 순위를 만들 수도 없다(FR-FLOW-06 · FR-LRN-09 · P6).
> 평가자 · 피드백 작성자의 익명성은 "저장하지 않는 것"이 아니라 "응답에 담지 않는 것"으로 지킨다. 서버는 1인 1회와 중복 방지를 확인하려고 작성자를 저장한다. 4인 팀에서는 평가자가 3명뿐이라 추천·비추천 이유 문장만으로도 작성자를 짐작할 수 있다 — 팀은 이것을 문제로 보지 않는다(2026-10-29 결정). 익명은 화면에 이름을 내보내지 않는 것까지다.
