## 1. 요구사항 확정

### MVP 범위

> 기능 이름은 04-features.md 트리거 열 그대로, R 은 04 의 R 열(정의서 ID · NFR · CON), S 는 02-workflow.md 에서 그 기능이 나오는 단계, P 는 05-policy.md 「대상 F」 열을 역으로 모은 값이다(04 의 「정책(P)」 열과 같아야 한다). 기능 그룹 F1~F11은 모두 문서에 있지만 **그룹이 있다고 세부 요구사항이 모두 Must인 것은 아니다** — 확정 범위는 아래 「채택 상태별 요구사항」 표를 따른다. F5 · F8 은 기능 전체가, F6 · F7 · F11 은 일부 요구사항이 [제안](requirements-changes.md 상태 "검토 중")이다. 대상 환경은 1024px 이상 노트북 · 태블릿의 웹 서비스다 · 01-problem.md 「대상 환경」.

## 2. 개요와 목표

> 01-problem.md 「4요소」 · 「프로젝트 한 줄 정의」와 기획안 「프로젝트 개요」 · 「프로젝트 목표」를 옮겼다.

| 항목 | 내용 |
| ---- | ---- |
| 프로젝트명 | 팀 오피스 v1 (부트캠프 팩) |
| 한 줄 소개 | 팀 레포가 3D 사무실이 되어, 회의실 토론으로 배우는 과정이 보이고 막힘은 먼저 드러나며 배운 것은 면접에서 쓸 수 있는 글로 남는다 |
| 형태 | 웹 서비스, 기존 3D 팀 오피스 위에 구축 (CON-05), 1024px 이상 노트북 · 태블릿 (NFR-07) |
| 팀 · 기간 | 4명 · 2주 (ASM-01) |
| 대상 (v1) | 부캠 19명, 5개 조 중 우리 조 하나. 공간 범위는 우리 조 레포 1개 (ASM-02) — 등록 레포 수는 열린 질문 |
| GitHub 연동 | 읽기 전용 (CON-02), 웹훅 없이 폴링 (CON-03) |
| 핵심 원칙 | 활동량이 아니라 흐름을 보여주고, 점수 · 순위 · 채점은 두지 않는다 |

**목표**

1. PR, 이슈, 도움 요청, 배운 점 공유, 기타 무엇이든 회의실 안건으로 올려 함께 토론하는 과정을 3D 사무실에서 보이게 해서 배움의 흐름을 만든다 (F9 · [제안] F5).
2. 팀 레포 하나를 사무실로 보여주고, 요구사항을 구역으로 나눠 명세 → 이슈 → PR 사슬을 한눈에 보이게 한다 (F3 · F4).
3. 활동량이 아니라 막힘, 대기, 편중을 보여줘서 도움이 필요한 사람을 먼저 드러낸다 (F6).
4. 코드 밖의 기여까지 포함해 개인 회고 리포트로 정리한다. 면접 꼬리질문 연습은 후순위로 둔다 (F11 · [제안] F8).

## 3. 발표 포인트

> 기획안 「기대 효과 및 향후 확장」의 발표 포인트를 옮겼다. 1 · 2 · 4 · 5의 투표 · 회의실 안건 · 코드 밖 기여 · 학습 타임라인은 [제안] 기능이라, 채택되지 않으면 발표 범위도 함께 다시 본다.

1. 부캠에서는 PR을 두고 의견을 나누고 토론하는 과정 자체가 학습이라는 관점에서 출발한 LMS라는 점
2. 누구나 무엇이든 회의실 안건으로 올려, 팀이 함께 토론하며 배우는 구조
3. 팀의 작성 방식을 바꾸지 않고 GitHub를 그대로 읽는 구조 (CON-01, CON-02)
4. 점수 대신 흐름을 보여주고, 코드 밖 기여는 팀원 확인으로 기록하는 설계와 그 이유
5. 우리 조가 직접 시범 운영한 데이터와 각자의 학습 타임라인, 회고 리포트로 시연
