GitHub 레포의 직접 수정 권한은 앱 역할과 별개다. 레포 관리자와 강사가 같은 사람인 경우는 운영상 없다고 전제하고, 서버는 레포 관리자가 자기 자신을 지정하는 요청을 거부한다. 강사 지정 전에 남긴 평가 · 안건 · 코멘트는 지우지 않고, 지정 뒤에는 강사 정책(P13)을 적용한다. 해제하면 그 사무실의 강사 권한이 즉시 끝나고, 과거 강사 답변 · 피드백은 보존한다. 심사용 ID/PW 계정의 역할은 P15를 따른다. 접근 권한은 현재 GitHub 자격과 앱의 강사 지정 상태를 함께 검사한다(2026-11-01 결정). GitHub 권한은 로그인할 때 한 번 확인해 세션에 두고 요청마다 GitHub에 다시 묻지 않으며, 세션은 30분\~1시간 뒤 만료된다(2026-10-28 결정). 강사 지정 여부는 요청마다 앱 DB에서 확인하므로 지정 · 해제가 바로 반영된다 · FR-AUTH-06(2026-10-30 결정). 권한은 화면이 아니라 API에서 요청마다 확인하고, 버튼을 숨긴 것을 권한 확인으로 보지 않는다 · FR-AUTH-04 | 요청이 거부되고 `{ "error": { "code": "forbidden_role", "message": "..." } }` 에러가 돌아온다. 화면 문구는 [?] (기획안에 없음) |
| P2 | F2, F3, F10, F12 | 레포 관리자(ROLE-02), 참여자(ROLE-01), 강사(ROLE-04) | 사무실 상태 = "열리지 않음" · "열림" | GitHub 조직이 가장 큰 단위이고 조마다 별도 조직이며, 앱은 조마다 조직에 설치한다. 학생(참여자 · 레포 관리자)은 자기 조 조직의 레포만 보고, 강사는 자신이 강사로 지정된 모든 조의 사무실을 본다 · FR-AUTH-07(2026-10-30 결정 — 정의서 ASM-02와 다름). 조 간 비교 화면 · 수치는 강사에게도 없다. 조직 안의 레포를 여러 개 등록할 수 있고, 상단 바 레포 드롭다운으로 다른 레포의 사무실로 전환한다 — 층별 사무실이 아니며 한 화면에는 항상 사무실 하나만 보인다(2026-10-28 결정 — 정의서 ASM-02 · FR-GH-01의 "1개"와 다름, requirements-changes.md 「범위」). 레포 등록(사무실 열기)과 팀 설정(프로젝트 기간 · FR-PLAN-01, 명세 문서 경로 · FR-REQ-01, 기준값, 강사 지정 · FR-AUTH-06)은 레포 주인인 레포 관리자만 할 수 있다. 요구사항–이슈 연결(FR-REQ-04)과 연결 후보 승인(FR-REQ-03)은 레포 관리자(ROLE-02)만 할 수 있다(03-requirements.md 행위자 · 2026-10-28 결정). 여러 조가 같은 서버 1개 · 공통 DB를 쓰고, 데이터는 사무실(Workspace — 등록된 레포 1개) 단위로 나뉜다. 사용자는 접근할 수 있는 Workspace의 데이터만 받고, 강사는 지정된 Workspace에만 접근한다 — REST뿐 아니라 SSE 같은 실시간 갱신에도 같은 검사를 한다(2026-11-01 결정). 시연용 Workspace(Demo Workspace)는 Fake/Seed 데이터로 채우고 "시연 데이터" 표시를 붙이며, 다른 조의 실제 데이터처럼 보이지 않게 한다. 시연 Workspace에도 인증 · 접근 검사를 그대로 적용한다. **시연 Workspace에는 명시적으로 등록한 대상만** 들어간다 — 우리 조의 실제 GitHub 계정, 그 시연 Workspace에 지정된 강사 계정, 발급한 심사용 계정(P15). GitHub로 로그인만 한 일반 사용자는 들어갈 수 없다(2026-11-01 추가 결정). **운영 범위**(2026-11-01 추가 결정): v1의 실제 운영은 우리 조 사무실과 시연 사무실이고, 다른 조가 실제로 가입해 쓰는 것은 필수 목표가 아니다. 여러 사무실 데이터 분리 · 레포 전환 · 강사의 여러 사무실 조회 · 공용 컨벤션 라이브러리 · 서버 측 접근 제어는 그대로 두고, 외부 조직 자동 가입 · 온보딩 · 운영자 대시보드 · 승인 워크플로 같은 범용 운영 기능은 만들지 않는다 | 참여자가 열리지 않은 레포를 고르면 "아직 사무실이 열리지 않았어요" 안내와 팀장 이름. 앱 접근이 허용되지 않은 조직은 자물쇠와 안내, "승인 요청하기". 팀 설정을 바꾸거나 요구사항–이슈를 연결하려는 ROLE-01 · ROLE-04의 요청은 `forbidden_role`. 접근할 수 없는 사무실(지정되지 않은 강사의 요청, 등록되지 않은 사용자의 시연 사무실 요청 포함)의 요청은 사무실이 있는지 드러내지 않도록 `not_found`(구현 기본값 — 2026-11-01 추가 결정) |

## 상태값

GitHub에서 읽은 원본 상태와 앱이 정하는 상태를 나눠 적는다. 원본 상태는 앱이 바꾸지 않고 다음 동기화에 반영만 한다(P3).

- **사무실**: 열리지 않음 → 열림 · 전이 조건: 레포 관리자가 레포를 등록하고 프로젝트 기간을 입력하면 열림. 명세 문서 경로는 건너뛸 수 있고(FR-REQ-01), 활동 기록 수집 동의도 열기 단계에 든다(FR-ACT — 2026-10-28 추가 결정) · P2 · P12
- **동기화**: 정상 ↔ 실패 · 전이 조건: 폴링·수동 동기화가 실패하면 정상→실패(마지막 성공 시각과 사유를 남기고 화면은 마지막 데이터 유지), 다음 동기화가 성공하면 실패→정상 · P4
- **이슈 · PR 원본 상태 (GitHub)**: 이슈는 담당자 유무 · 열림 · 닫힘, PR은 열림 · Draft · 리뷰 요청 · 머지 · 닫힘(머지 안 됨) · 전이 조건: GitHub에서 바뀐 값이 다음 동기화에 반영될 때. 앱에서는 바꾸지 않는다 · P3. 이슈와 PR은 다른 엔티티이고, "닫힌 이슈 = 머지된 PR"로 가정하지 않는다(2026-11-01 결정)
- **표시 상태와 공간 역할 (원본 상태에서 계산 — 2026-11-01 결정)**: 아래 대응만 확정이고, 가구 이름은 기본 테마(사무실)의 표현이다(ARCHITECTURE.md 「공간 역할과 테마」) · P3

  | 대상 | 원본 상태 | 표시 상태 | 공간 역할 (기본 테마 표현) |
  | --- | --- | --- | --- |
  | 이슈 | 열림 · 담당자 없음 | 대기 | 대기 공간 (백로그 선반) |
  | 이슈 | 열림 · 담당자 있음 | 작업 중 | 대표 담당자 작업 공간 (담당자 책상) — 담당자가 여럿이면 대표 담당자 한 사람의 공간에 상자 하나만 놓는다(2026-11-01 추가 결정) |
  | 이슈 | 닫힘 | 완료 또는 종료 — GitHub 닫힘 사유(완료 · 계획 안 함)로 구분할 수 있다(구현 기본값) | 완료 공간 (완료 선반) |
  | PR | 열림 | 검토 | 검토 공간 (검토 영역) |
  | PR | 머지 | 완료 | 완료 공간 (완료 선반) |
  | PR | 닫힘(머지 안 됨) | 종료 — 미병합 종료 표시(구현 기본값) | 완료 공간 (완료 선반) — GitHub에서 머지 · 닫히면 완료 선반으로 간다(FR-LRN-07 · 2026-10-29 결정) |
  | PR | Draft | 검토 — Draft 배지(구현 기본값) | 검토 공간 (검토 영역) |

  평가 결과는 위치를 바꾸지 않는다(머지 준비 선반 없음 — 2026-10-29 결정). 요구사항 연결과 회의 안건도 위치를 바꾸지 않는다 — 요구사항 구역으로 드래그하면 `RequirementLink`만 생기고 객체는 기본 위치로 돌아가며, 회의 공간으로 드래그하면 원본은 그대로이고 별도 `AgendaItem`의 표현이 회의 공간에 놓인다(2026-11-01 결정). 대표 담당자는 결정적인 규칙으로 고르고(규칙은 구현 기본값 — CONTRACTS.md 「10」), 상세 화면에는 모든 담당자를 보인다(2026-11-01 추가 결정). "구현 기본값"은 합의된 기본값으로 시작해 구현 중 바꿀 수 있는 값이다 — 목록은 CONTRACTS.md 「10」
- **아바타 위치 (2026-11-01 결정)**: 기본은 본인 작업 공간. 회의 같은 앱 내부 이벤트에 따라 움직일 수 있다(회의 시작 · 종료 같은 앱 내부 이벤트를 우선한다 — 구현 기본값, 2026-11-01 추가 결정). 사용자가 아바타를 직접 움직이는 기능은 Must가 아니고, 생기더라도 3D 인터랙션일 뿐 이슈 상태 · 담당자를 바꾸지 않는다. 강사는 아바타가 없다(P13)
- **회의 안건**: 확정 → 회의 완료(메모 표시, 기획안의 "회의를 거친 항목") · 후보(반투명) → 확정(불투명) · 확정 · 후보 → 거둠 · 전이 조건: 회의에서 결정과 배운 점을 기록하면 회의 완료(FR-MTG-03 · 04). 앱이 찾은 후보를 버튼이나 드래그로 확정, 사람이 직접 만든 안건(배운 점 공유, 기타)은 바로 확정. 확정 뒤 회의 전에는 올린 사람이 거둘 수 있다. 거둔 안건과 확정되지 않은 후보는 지우지 않고 "거둠"으로 남긴다(2026-10-28 결정) · P8. PR이 회의 안건이 되어도 PR 평가는 그대로다 — 안건은 평가와 따로 붙는 별도 항목이다(FR-LRN-04 "평가 결과와 상관없이"). 안건 상태는 원본 이슈 · PR의 표시 상태 · 위치와 따로 움직인다(2026-11-01 결정)
- **도움 요청 (FR-LRN-15\~20)**: 열림 → 논의 중 → 해결(닫힘) · 미해결 시 논의 중 → 안건 후보 → 안건 → 종료 · 전이 조건: 팀원이 코멘트하면 논의 중, 요청자가 닫으면 해결(도움이 된 코멘트와 배운 점 한 줄을 남김), 48시간 안에 해결되지 않으면 안건 후보(FR-LRN-18 · 2026-10-28 추가 결정), 요청자가 전환하거나 후보가 확정되면 안건, 회의에서 해결되거나 이슈로 만들기로 결정하면 종료 · P8. 강사 답변은 상태를 바꾸지 않는다(FR-LRN-21 · 2026-10-30 결정). 근거: FR-LRN-15\~20(requirements-changes.md 「1. 추가」)
- **기술 결정 카드**: 본인 확인 전 → 확인됨 · 전이 조건: 본인이 칸을 확인하고 "내가 배운 점"을 쓰면 확인됨 · P11
- **활동 기록**: 확인 대기 → 확인됨 · 전이 조건: 작성자 외 1명 이상이 확인하면 확인됨 · P12
