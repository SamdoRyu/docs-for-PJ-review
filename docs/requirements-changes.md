# 요구사항 변경안 — 정의서 v0.1 대비

기획안(팀 오피스 v1 기획안)이 요구사항 정의서 v0.1에 더하거나 바꾼 것을 정의서 형식으로 모은 문서다. 정의서 PDF는 수정하지 않고, 팀이 채택하면 정의서 다음 버전과 변경 이력에 옮긴다.

- 출처: `docs/plan/` 의 기획안. 요구사항과 수용 기준 문장은 기획안 원문을 그대로 옮겼다.
- 상태: `검토 중` → 팀 결정 후 `채택` 또는 `제외`. 지금은 모두 `검토 중`이다.
- 충돌하면 기획안 > 개발 컨벤션 > 정의서 순으로 따른다.
- **원본 확인 필요**: 정의서 v0.1 PDF가 레포에 없다. 들어오면 "수정"과 "범위" 절의 정의서 원문 칸을 채운다. 원문이 없는 ID 목록과 영향 범위는 03-requirements.md 「원본 확인 필요 요구사항」에 있다.
- **[제안] 표기 (docs 공통 규칙)**: 이 문서에서 `검토 중`인 요구사항이나 「5. 추가 제안 후보」에 기대는 부분이 읽는 사람에게 보이게 `[제안]`을 붙인다. 행 · 항목 단위로 붙이면 되고, 확정 요구사항과 섞인 행은 제안 부분 앞에 한 번만 붙인다 — 확정 요구사항도 쓰는 항목(예: 회의 안건)에 통째로 붙이지는 않는다. 채택되면 태그만 지우면 되고, 개수 집계나 이력 기록은 따로 하지 않는다. 우선순위 열의 값은 "제안 우선순위"로 읽는다 — 채택 전에는 Must라도 확정 MVP 범위가 아니다.
- 「5. 추가 제안 후보」는 기획안에 동작이 서술되어 있지만 요구사항 ID가 없는 것이다. ID를 아직 주지 않았고, 팀이 ID를 줄지 정한다.

정함(2026-10-28 결정 회의): 아래 세 가지 모두 Git 전략 쪽을 쓴다. 기획안 예시와는 다르다.

- 브랜치 이름: 기획안 피드백 예시는 `type/#이슈번호-설명`(`fix/#18-login-fix`), 개발 컨벤션 Git 전략의 등록 패턴은 `#` 없는 `<type>/<이슈번호>-<slug>`다.
- PR 제목: 기획안 검사 대상 표는 `[type] 설명`, Git 전략 「3. 커밋과 PR 제목」은 커밋 메시지와 같은 Conventional Commits 형식(`feat(sync): …`)이다.
- PR 템플릿 경로: 기획안 검사 대상 표는 `.github/pull_request_template.md`, 레포 파일과 Git 규칙은 `.github/PULL_REQUEST_TEMPLATE.md`다. FR-HAB-02가 규칙 파일을 찾을 때 대소문자를 구분할지 함께 정한다.

## 6. 우선순위 검토 메모 (변경 아님)

아래는 문서를 맞추다 나온 검토 거리다. 우선순위 값은 바꾸지 않았고, 팀이 정하면 위 표와 정의서에 반영한다.

- **FR-LRN-06 재투표 (Should)**: FR-LRN-01~03은 Must인데 재투표가 Should라서, FR-LRN-06 없이 구현하면 새 커밋이 올라와도 이전 투표가 그대로 남는다. Must로 올릴지, 또는 FR-LRN-06이 없을 때 새 커밋의 투표 처리를 따로 정할지 결정이 필요하다. 개선안: 투표 회차마다 투표 시점의 PR 최신 커밋을 함께 남겨, 어떤 커밋에 대한 찬성·반대인지 보이게 한다(구현 구조는 미정).
- **FR-LRN-03 "반대 0"**: 수용 기준은 "기준값(기본: 3명 중 2표)"만 적고, "반대가 없으면"은 기획안 「배움의 흐름」 본문과 05-policy.md P7에만 있다. 채택할 때 수용 기준에 넣을지 정한다.
- **FR-HAB-01 확정 부분과 Git 전략**: 2026-10-28에 `develop`을 없애 PR이 `main`으로 가고 `Closes #N`만 쓴다. 그래서 FR-HAB-01은 closing keyword만 인정하는 원래 기준대로 구현하고, `Refs #N` 수정안은 철회했다.
- **정의서 용어와 FR-LRN**: 코드 컨벤션(BE)의 용어 표는 "찬성·반대 투표(`Vote`)"와 "회의 안건(`AgendaItem`)"을 정의서 1.3 용어로 둔다. 정의서 v0.1에 투표가 이미 있다면 위 「1. 추가」의 FR-LRN 일부는 추가가 아니라 수정일 수 있다 — 원본 확인 필요.
- **FR-LRN-05 "그대로 머지" 결정**: 반대표가 남아 있는 PR을 회의에서 "그대로 머지"로 정했을 때 FR-LRN-03의 머지 준비(반대 0)와 어느 쪽이 우선하는지 기획안에 없다.
- **FR-GH-05 (Should·Could)**: 상단 바의 동기화 상태 표시는 Should·Could지만, "동기화 실패를 삼키지 않고 마지막 성공 시각과 사유를 남긴다"는 코드 컨벤션(BE)과 NFR-09가 이미 요구한다. 표시까지 Must로 올릴지 정한다.
- **FR-REP-01 영역 라벨 모음의 이름**: 정함(2026-10-28) — "담당 기능 영역"으로 부른다. 영역 라벨(`area:*`)은 기술 스택이 아니라 기능 영역이다.
